# إجراءات الاستجابة للحوادث السيبرانية

**الإصدار** 1.0 · **التاريخ** 2026-11-12 · **قائد الاستجابة** مدير النظام · **التصعيد** راعي المشروع.

## ما يُعد حادثاً
دخول غير مصرح، تسرب أو حذف بيانات، تسرب مفتاح سري، تعطل النظام أكثر من 4 ساعات، رسائل احتيالية باسم النظام، فقدان جهاز أو حساب مستخدم.

## المراحل
| المرحلة | الإجراء | المسؤول | المدة |
|---|---|---|---|
| 1. الاكتشاف والإبلاغ | أي مستخدم يبلغ مدير النظام فوراً بالبريد أو الجوال | الجميع | فوري |
| 2. التقييم | تحديد النوع والنطاق والبيانات المتأثرة من سجل التدقيق | مدير النظام | خلال ساعة |
| 3. الاحتواء | حذف المستخدم المشتبه أو تعطيله، تغيير كلمة المرور، تدوير المفتاح المتسرب (Resend، رموز السكربت)، تقييد القواعد مؤقتاً | مدير النظام | خلال 4 ساعات |
| 4. الإبلاغ | إبلاغ الراعي. وإن مسّ بيانات شخصية: تقييم الإبلاغ للهيئة السعودية للبيانات والذكاء الاصطناعي خلال 72 ساعة وإبلاغ أصحاب البيانات عند الضرر. وإن كان حادثاً سيبرانياً جوهرياً: إبلاغ الأمن السيبراني بالجهة | مدير النظام والراعي | خلال 72 ساعة |
| 5. الاستعادة | الاسترجاع من النسخة الاحتياطية (restoreFromBackup) أو من GitHub للكود، والتحقق من سلامة البيانات | مدير النظام | حسب الحادث |
| 6. الدروس المستفادة | تقرير مختصر: السبب، الأثر، ما تم، وما يمنع التكرار، وتحديث سجل المخاطر | مدير النظام | خلال أسبوع |

## إجراءات سريعة
- **تسرب مفتاح Resend:** حذفه من لوحة Resend، إنشاء جديد، وضعه في Script Properties باسم RESEND_KEY.
- **حساب مستخدم مخترق:** حذفه من الإعدادات > المستخدمون (يمنع القراءة فوراً عبر القواعد)، ثم من Firebase Authentication.
- **حذف بيانات بالخطأ:** listBackups ثم restoreFromBackup لأحدث نسخة قبل الحذف.
- **تعطل الموقع:** التحقق من GitHub Pages وحالة Firebase، والعمل مؤقتاً من مرآة Google Sheets.
